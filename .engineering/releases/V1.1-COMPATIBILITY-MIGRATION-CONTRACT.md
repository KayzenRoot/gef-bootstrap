## 1. Governing principles

1. **Preservation-first.** Existing user work is never discarded to satisfy GEF structure (`D-0013`, `D-0014`, README: *"Never delete or overwrite user work merely to satisfy bootstrap structure"*).
2. **Fail-closed on unsafe ambiguity.** Unknown or conflicting compatibility evidence must not resolve optimistically. `V1.1-SCOPE.md` requires preservation-first migration with rollback/roll-forward evidence.
3. **Progressive normalization.** Prefer index/alias/adapt over big-bang rewrite (`D-0014`). Shadow assurance is required before aggressive proof/test reuse becomes authoritative in an adopted project.
4. **No silent mutation.** Every managed-file change is planned, staged, verified and receipted (`ARCHITECTURE.md` A5).
5. **Descriptive ≠ normative.** Observed/implemented state and approved/required state are recorded separately; a mismatch produces a drift record and never silently rewrites either side (`D-0015`).

### 2.1 Unknown handling

Any dimension whose value cannot be determined is `UNKNOWN`. A result containing `UNKNOWN` on a **blocking** dimension resolves to `INDETERMINATE`, not `SUPPORTED`. This mirrors the existing fail-closed posture of `doctor(observations)` (which yields `UNKNOWN` for unobserved ids) and `securityAudit()` (which yields `INDETERMINATE` when unobserved).

## 3. Classification of managed-file drift

The matrix skeleton carries the classification vocabulary; the contract fixes the semantics.

| State | Meaning | Permitted action |
|---|---|---|
| `CURRENT` | matches the fingerprint GEF last wrote | none required |
| `STALE` | differs only by a known GEF-originated prior version | migrate, with receipt |
| `USER_MODIFIED` | differs from GEF's recorded fingerprint in user-owned content | **never overwrite**; offer merge/adapt or leave |
| `CONFLICTING` | user content and required GEF content both changed incompatibly | `RECOVERY_REQUIRED` / escalate; no automatic resolution |
| `ABSENT` | not present | create only if the operation's scope authorizes creation |
| `UNKNOWN` | cannot be determined | fail closed; escalate |

`USER_MODIFIED` and `CONFLICTING` are the two states that most commonly cause silent damage; both MUST require explicit operator authorization before any write.

## 4. Upgrade behaviour contract

### 4.1 Mandatory phases

```text
PREVIEW  →  COMPATIBILITY CHECK  →  MIGRATION PLAN  →  DRY-RUN  →  APPLY (transactional)  →  VERIFY  →  RECEIPT
                                                                        │
                                                                        └─► RECOVERY_REQUIRED on failure
```

`ARCHITECTURE.md` A9 already requires: *"Updates follow preview → compatibility check → migration plan → apply → verify → recovery/rollback where possible. Silent self-update is not the default."*

### 4.2 Dry-run

- A dry-run MUST be side-effect free and MUST report the same plan digest as the subsequent apply for unchanged inputs.
- Existing verified primitive: `upgradePreview(current, candidate, migrations)` returns `NOOP` (equal versions), `INDETERMINATE` (missing input) or `READY` with a `digest`. WO-004 reuses this and extends it with drift classification.

### 4.3 Transactional apply

Apply MUST use the kernel envelope (`ARCHITECTURE.md` A5): bind expected pre-state → build plan → validate allowed surface → capture recovery material → stage in same-filesystem temp → verify staged content/schemas/fingerprints → atomic apply → verify post-state → emit receipt.

Pre-existing verified primitives in `packages/kernel/src/`: `transaction-plan.ts`, `transaction-dry-run.ts`, `transaction-apply-governed.ts`, `transaction-apply-certified.ts`, `transaction-rollback-authoritative` variants, `transaction-recovery-types.ts`, `transaction-idempotency.ts`, plus filesystem safety (`authorizeFilesystemPath`, `proveFilesystemTraversal`, `evaluateFilesystemOverwrite`, `composeFilesystemPhysicalSafety`). WO-004 MUST consume these.

### 4.4 Rollback / roll-forward

| Situation | Required behaviour |
|---|---|
| Failure before post-state verification, recovery material complete | restore affected managed surface; terminal state `RECOVERED` |
| Failure with incomplete recovery material | terminal `RECOVERY_REQUIRED`; no silent partial state |
| Partial external (provider) effect | modelled as a saga, not a false atomic claim (`A5`); record forward + compensating action |
| Roll-forward required (rollback unsafe) | permitted only when explicitly declared before apply, with evidence |

`recoveryPlan` and `backupManifest` in `packages/security-reliability-integrations/src/index.js` are the existing recovery surfaces; `freezeReceipt` provides the receipt binding.

### 4.5 Unsupported-path behaviour

| Case | Required outcome |
|---|---|
| Version pair not in the supported matrix | `UNSUPPORTED`, exit `40` (`DEPENDENCY_OR_CAPABILITY_FAILURE`), no mutation |
| Schema major unknown forward | fail closed (`A8`: unknown required major version fails closed) |
| Node below declared `engines` | `UNSUPPORTED`, no mutation |
| Platform not `win32`/`linux`/`darwin` | `UNSUPPORTED` (existing `installPlan` returns `{state:'UNSUPPORTED'}` for non-listed platforms) |
| Provider capability absent | capability gap, not silent bypass (`D-0040`, README boundary) |
| Ambiguous managed-file state | `INDETERMINATE`/`RECOVERY_REQUIRED`; never optimistic |

### 4.6 Hotfix forward-port interaction

A `1.0.x` hotfix correction that is still applicable to `release/1.1` MUST be forward-ported (`ADR-0003-D2`). The upgrade contract MUST therefore treat "correction present in `1.0.x` but absent in `1.1.x`" as a migration case, with the originating hotfix identity recorded in the receipt.

## 5. Non-goals

- Automatic destructive repair (`repairSuggestion` already returns `automatic:false`, `previewRequired:true`; preserved).
- Big-bang normalization of brownfield repositories.
- Silent self-update.
- Rewriting accepted V1 evidence, checkpoint state or the `v1.0.0` tag.
- Cloud dependency for core local operation (`V1.1-SCOPE.md` OUT OF SCOPE).
