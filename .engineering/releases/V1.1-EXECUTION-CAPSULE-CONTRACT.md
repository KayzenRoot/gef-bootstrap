## 1. Definition

An **Execution Capsule** is the minimum sufficient, fingerprinted execution context for one bounded, Work-Order-authorized increment. It answers, without rediscovery: what must be read, what may be written, what is forbidden, what constrains the change, what proves it, which tests are selected, which prior proofs remain reusable, and when to stop.

It is the compile target of `Task Context Compiler` (M14 / `packages/task-context-compiler`) and `Execution Pack Compiler` (M15 / `packages/execution-pack-compiler`), projected through the acceleration mechanisms owned by M63. Existing verified symbols relevant to the projection: `navigationPlan` and `executionWaves` in `packages/m62-m63-final/src/index.mjs`.

## 3. Determinism

**Requirement:** compiling the same authoritative inputs at the same base must produce a byte-identical capsule and an identical `capsuleFingerprint`.

Determinism rules:

1. **Canonical serialization.** JSON with stable key ordering, no insignificant whitespace, LF line endings, UTF-8 without BOM. Arrays whose order is not semantically meaningful MUST be sorted (`navigation.*`, `affected.symbols`, `affected.dependencies`, `selectedTests.tests`); the schema enforces `uniqueItems` and ordering is asserted by test.
2. **Declared canonicalization.** `fingerprints.canonicalization` MUST name the algorithm. A capsule without a declared canonicalization is non-conforming.
3. **No volatile inputs.** Wall-clock time, host names, absolute machine paths, locale, and iteration order of unordered collections MUST NOT enter the fingerprint input set. `expiresAt` is excluded from the fingerprint projection.
4. **Explicit identity derivation.** `capsuleId` is derived from the capsule content, not assigned ad hoc. Two capsules with identical bindings must collide; two with any different binding must not.
5. **`base.headSha` + `base.treeFingerprint`** bind the capsule to exact subject state (`D-0036`).

Determinism is a testable property, not a claim: WO-005 MUST show a repeat-compilation equality test (see T-MATRIX `CTX-DET`).

## 4. Invalidation semantics

Invalidation follows the `DOCUMENT → SECTION → FACT → DEPENDENCY SET` hierarchy (`D-0023`): the smallest safe authoritative granularity, so that a change invalidates only dependent capsules.

| Trigger | Drift class | Required response |
|---|---|---|
| no relevant input changed | `NONE` | capsule remains valid |
| non-semantic change (formatting, comments outside bound facts) | `LOCAL_COMPATIBLE` | capsule remains valid; record drift |
| bound source content changed | `SEED_RECOMPILE_REQUIRED` | `state: STALE`; executor MUST NOT proceed on stale instructions |
| dependency endpoint unknown | `CONTEXT_EXPANSION_REQUIRED` | bounded expansion, then recompile |
| contradictory evidence between inputs | `CONFLICT` | `state: REJECTED`; halt and escalate |

`invalidation.onDrift` selects executor behaviour: `RECOMPILE`, `EXPAND_CONTEXT`, `ESCALATE`, `HALT`. There is no "continue optimistically" option.

The pre-existing **Seed Drift Sentinel** classification in `EXECUTOR-ACCELERATION-CONTRACT.md` §13 is reused verbatim; this contract adds the capsule-state mapping in the table above.

## 5. Fail-closed rule (mandatory)

The capsule MUST fail closed when context certainty is insufficient.

1. `certainty: INSUFFICIENT` ⇒ `state` MUST be `INDETERMINATE` (enforced by schema `allOf`). An indeterminate capsule MUST NOT be handed to an executor as an execution instruction.
2. `state: COMPILED` ⇒ `certainty` MUST be `SUFFICIENT` (enforced by schema).
3. An `UNKNOWN` blocking dimension (`V1.1-COMPATIBILITY-MIGRATION-CONTRACT.md` §2.1) forces `certainty: INSUFFICIENT`.
4. Missing dependency-closure knowledge MUST NOT be converted into a smaller test radius (`EXECUTOR-ACCELERATION-CONTRACT.md` §16).
5. `openQuestions` MUST NOT be emptied by inventing answers. Unresolved remains unresolved and escalates (`ADR-0002-D1`).
6. A capsule MUST NOT authorize mutation of the production branch: `base.productionBranchTouched` is `const false`.

Positive-value obligations: `constraints` and `selectedTests.escalation` are non-empty by schema, so a capsule cannot be compiled with "no constraints" or "no escalation possible".

---

## 6. Relationship to the executor boundary

The capsule is an acceleration artifact, not an authority transfer. Per `ADR-0003-D2` bound 7 and `D-0047`:

- canonical sources remain authoritative; the capsule is a projection;
- the capsule MUST NOT decide scope admission, requirements, architecture intent, risk acceptance or review verdicts;
- the executor MUST NOT claim `APPROVED`; acceptance is external;
- proof reuse referenced by a capsule can never manufacture production credit (`proofReferences[].manufacturesProductionCredit: const false`).
