## 1. Governing rules

1. **Targets are not results.** Goals in `V1.1-RELEASE-PLAN.md` remain benchmark *targets* until measured (`D-0039`, `D-0050`). A design document MUST NOT report an improvement.
2. **Incomparable populations are reported as incomparable.** Never converted into a speedup claim.
3. **Quality invalidates optimization.** A correctness, security, recovery or evidence-integrity regression invalidates any claimed gain, even when time or tokens improve (`EXECUTOR-ACCELERATION-CONTRACT.md` §15, `D-0019`).
4. **Modernization is not a comparison.** Different toolchains, Node lines, hardware classes or workload scopes are different populations.
5. **Measured, estimated and unavailable are distinct** and MUST be labelled (`D-0050`).

Existing verified primitives the implementation must reuse rather than reinvent:

| Symbol | Source | Behaviour |
|---|---|---|
| `performanceRegression(baseline, candidate)` | `packages/m62-m63-final/src/index.mjs` | returns `INCOMPARABLE` when `population` differs; otherwise `REGRESSION`/`NO_REGRESSION` |
| `executorBudget({latencyMs, tokens, acceptedPoints, ioOps})` | `packages/m62-m63-final/src/index.mjs` | returns `MEASURED` |
| `compareBenchmark` | `packages/m41-m47-platform/src/index.mjs` | benchmark comparison |
| `benchmarkSummary`, `performanceGate` | `packages/m55-m61-quality/src/index.mjs` | summary + gate |

`performanceRegression` already encodes rule 2 in code: mismatched `population` ⇒ `INCOMPARABLE`. This protocol generalizes that guard.

## 2. Population identity (the comparability contract)

Two runs are comparable **only** when their population identity matches on every dimension below. Any mismatch ⇒ `INCOMPARABLE`.

| # | Dimension | Examples |
|---|---|---|
| P1 | Workload kind | greenfield init, brownfield adopt, upgrade/apply, doctor, context compile, validation selection |
| P2 | Workload instance identity | the exact fixture/work-order identifier and its digest |
| P3 | Base state | commit SHA + tree fingerprint of the starting state |
| P4 | Toolchain | Node version, npm version, TypeScript version, package manager |
| P5 | Platform | OS + version + architecture |
| P6 | Assurance policy | ladder level, whether a final sweep was required |
| P7 | Cache/proof posture | cold (no reusable proofs) vs warm (declared reusable proof set) |
| P8 | Measurement boundary | what is inside the timed region (process start? compile? validation? total?) |

P4–P6 and P8 mismatches are the most common accidental "speedups". A candidate measured on a faster machine, newer Node or a warmer cache than its baseline is **not** an improvement.

## 3. Metrics

Metrics are grouped by the three cost axes of `D-0005`/`D-0011`/`D-0012` (token, latency, engineering effort). Each MUST carry `{value, unit, source: MEASURED | ESTIMATED | UNAVAILABLE}`.

### 3.1 Latency
| ID | Metric | Unit |
|---|---|---|
| `M-LAT-01` | wall-clock duration of the executor invocation | ms |
| `M-LAT-02` | validation wall-clock (aggregate) | ms |
| `M-LAT-03` | final exact-head assurance duration | ms |

### 3.2 Context / source volume
| ID | Metric | Unit |
|---|---|---|
| `M-CTX-01` | context source volume (canonical sources read) | count |
| `M-CTX-02` | context payload size | bytes |
| `M-CTX-03` | files inspected | count |
| `M-CTX-04` | broad repository searches executed | count |
| `M-CTX-05` | context expansions (bounded escalations) | count |
| `M-CTX-06` | cache/seed invalidations | count |

### 3.3 Validation
| ID | Metric | Unit |
|---|---|---|
| `M-VAL-01` | tests/checks executed | count |
| `M-VAL-02` | duplicate test invocations avoided via reuse | count |
| `M-VAL-03` | test-proof reuse rate | ratio |
| `M-VAL-04` | full-suite invocations per Work Order | count |

### 3.4 Rework and outcome
| ID | Metric | Unit |
|---|---|---|
| `M-RWK-01` | retries | count |
| `M-RWK-02` | correction loops | count |
| `M-RWK-03` | rework ratio | ratio |
| `M-OUT-01` | accepted increments completed | count |
| `M-OUT-02` | defects escaping selective validation | count |
| `M-OUT-03` | final disposition | enum |

### 3.5 Token metrics
`M-TOK-01` input tokens, `M-TOK-02` output tokens, `M-TOK-03` total token path per governed change (`D-0011`). Where the execution environment does not expose token counts, the metric MUST be recorded `UNAVAILABLE` — never estimated silently into a total.

### 3.6 Derived ratios
`Prompt Progress Density` (`EXECUTOR-ACCELERATION-CONTRACT.md` §15): accepted increments per invocation, accepted semantic units per input-token bucket, accepted progress per wall-clock unit, files correct before first correction, avoided rereads/searches versus baseline. Derived ratios inherit the comparability of their inputs; an incomparable input makes the ratio `INCOMPARABLE`.

## 4. Baseline procedure

1. **Freeze the population.** Select representative workloads and record P1–P8 for each. Baselines are captured on the V1.0.0-equivalent workflow before V1.1 acceleration is enabled.
2. **Representative workload set (planned).** At minimum: (a) greenfield `init` on a fixed fixture; (b) brownfield `adopt` on a fixed drifted fixture; (c) an `upgrade` apply on a fixed V1.0-style managed surface; (d) one governed implementation increment compiled and executed end-to-end; (e) validation selection on a fixed change set.
3. **Cold/warm separation.** Capture both a cold run (no reusable proofs) and a warm run (declared reusable proof set) and never compare across postures.
4. **Repetition.** Each measurement point is repeated; report dispersion, not a single sample.
5. **Immutability.** A baseline record is immutable once captured. Re-capturing produces a new baseline identity; the old one is retained for lineage.
6. **Storage.** Baseline records are repository-local derived state, inspectable and diffable (`ARCHITECTURE.md` A4). They are accelerators/evidence carriers, never canonical truth.
7. **No regression on quality gates.** Every benchmark run records the concurrent correctness/security outcome; a run whose quality gate failed cannot be used for an improvement claim.

---

## 5. Comparison and reporting

A comparison report MUST state, per metric: baseline population identity, candidate population identity, comparability verdict, values with units and source labels, dispersion, and quality-gate outcome.

**Verdict vocabulary:** `IMPROVED` · `NO_CHANGE` · `REGRESSION` · `INCOMPARABLE` · `INDETERMINATE`.

Rules:

- Any P-dimension mismatch ⇒ `INCOMPARABLE`. No numeric delta may be presented as a gain in that case.
- Missing data on a required metric ⇒ `INDETERMINATE`, not `IMPROVED`.
- A quality-gate failure ⇒ the optimization claim is void regardless of numbers.
- Percentages may be reported only from comparable, repeated measurements.

`V1.1-RELEASE-PLAN.md` goals (reduce context volume, reduce unnecessary validation, reduce rediscovery, no material regression) are reported against this protocol; none may be asserted as achieved before comparable baseline data exists.

## 6. CLI ROI obligation

`ADR-0003-D4` conditions the CLI admission on measurable ROI. WO-002/WO-008 MUST therefore produce a comparable comparison of at least one representative workload performed via the CLI versus the documented source-workspace/manual path, using this protocol. `INCOMPARABLE` or `INDETERMINATE` is an honest outcome and escalates to the owner as a scope finding — it is not silently rounded up to a benefit.

## 7. Acceptance obligations for WO-008

1. Every reported metric carries a source label (`MEASURED`/`ESTIMATED`/`UNAVAILABLE`).
2. Cross-population comparison is refused in code and in the report (negative test).
3. Baseline records are immutable and lineage-retaining.
4. At least one cold-vs-cold and one warm-vs-warm comparison is demonstrated.
5. A quality-gate failure demonstrably voids an apparent gain (negative test).
6. No token metric is presented as measured when the environment does not expose tokens.
