## 1. Position in the architecture

`ARCHITECTURE.md` A3 freezes **"library/application-API first, thin CLI second"**. The V1.1 CLI is therefore a transport and rendering surface, not a logic layer.

```text
  argv ──► CLI PARSER ──► CommandRequest ──► KERNEL CommandRegistry
            (thin)             │                    │
                               │                    ▼
                               │            CommandRegistration.handler
                               │            (domain engine delegation)
                               │                    │
                               │                    ▼
                               └─────────── HandlerOutcome<T>
                                                    │
                                    ┌───────────────┴───────────────┐
                                    ▼                               ▼
                          STRUCTURED RENDERER                 EXIT PROJECTION
                          (human | json)                      projectExitCode()
```

Forbidden by `ARCHITECTURE.md` dependency rules and upheld here:

- CLI handler containing business logic;
- CLI importing provider (GitHub) models directly;
- CLI reconstructing semantics from cache/derived state;
- CLI deciding scope, requirements, risk acceptance or review verdicts (`ADR-0003-D4`);
- CLI bypassing the kernel transaction envelope for filesystem mutation.

## 3. Command parsing boundary

### 3.1 Canonical command IDs

`canonicalCommandIdPattern` is `/^gef\.[a-z0-9][a-z0-9-]*\.[a-z0-9][a-z0-9-]*$/`. CLI verbs map to `gef.<noun>.<action>`; the parser MUST reject non-conforming IDs through the registry, not through a parallel validation path.

### 3.2 Parsing rules

- The CLI parser produces a `CommandRequest` (`commandId`, `contractVersion`, `input`, `targetRef?`, `expectedState?`, `authorizationRef?`, `deadlineMs?`).
- Input is validated by the registered `CommandRegistration.validateInput` (`InputValidator`), never by ad-hoc handler checks.
- `mutation` and `requiresTarget` declared on the registration govern whether a target binding is required; the CLI MUST honour them rather than hardcode per-command rules.
- Unknown command, malformed flag, missing required argument → `USAGE_OR_INPUT_ERROR` (`10`). The parser resolves this before any engine call.
- Argument separation: no shell string concatenation for subprocesses (`ARCHITECTURE.md` security baseline), reusing `createProcessSpec`.

### 3.3 Structured output contract

Two renderers over one result:

- `human` — default when stdout is a TTY.
- `json` — selected by `--json` or automatically when stdout is not a TTY.

The JSON envelope is a stable projection of `GefResult<T>`; it MUST carry at least: `ok`, `commandId`, `contractVersion`, terminal state, and either payload or structured `GefError` with `category`, `recoverability`, causes and `RemediationAction[]` where present. Machine consumers MUST NOT need to parse human text. Rendering is the CLI's only output authority; engine payloads are passed through without semantic reinterpretation.

## 4. Behaviour contracts

| Concern | Contract |
|---|---|
| Help | `gef --help` and `gef <verb> --help` render from `helpIndex`; content is deterministic and sorted by `id`. |
| Version | Deterministic string from a single provenance source (§5.1). `gef --version` never consults the network. |
| Non-interactive / CI | Default posture is non-interactive. Any prompt requires explicit opt-in; with no TTY the CLI MUST NOT block. Destructive actions are never auto-repaired (`repairSuggestion` returns `automatic:false`, `previewRequired:true` — preserved). |
| Dry-run | `preview`-class command IDs MUST be side-effect free; `apply`-class commands MUST pass through the kernel transaction envelope (`ARCHITECTURE.md` A5) and emit a receipt. |
| Filesystem safety | All mutation routed through kernel `authorizeFilesystemPath` → `proveFilesystemTraversal` → `evaluateFilesystemOverwrite` → `composeFilesystemPhysicalSafety` → `createFilesystemEffectAdapter`. Default-deny surface. |
| Error mapping | Exactly one mapping function: `projectExitCode`. No per-command exit codes. |
| Fail-closed | Unknown/absent evidence yields the failure/indeterminate state of the owning engine, never an optimistic default. |
| Secrets | Redaction through the existing redaction surface; the CLI never prints authorization references or tokens. |

### 4.1 Test seams

The CLI is testable without shell coupling (`ARCHITECTURE.md` A3/A10): the parser is a pure argv→`CommandRequest` function; the renderer is `GefResult→string`; engine delegation goes through `CommandRegistry`. Integration and E2E tests may additionally exercise the real process boundary (see `.engineering/releases/V1.1-TEST-MATRIX.md`).

## 5. Distribution strategy

### 5.1 Version provenance

One canonical version source, resolved at build time, read by `gef --version`, the packaged manifest and the release receipt. Divergence between them is a release defect. **Constraint:** today `package.json` declares the workspace at `1.0.0` while `packages/cli/package.json` declares `0.0.0`. WO-002 MUST reconcile version provenance to a single authority; WO-001 records the inconsistency rather than changing package metadata (out of scope).

### 5.2 Supported model for V1.1 (designed)

Layered, consistent with `ARCHITECTURE.md` A9:

1. **Source workspace** — the proven V1.0.0 path (`git clone`, `npm ci`, `npm run validate`). Preserved (`V1.1-SCOPE.md` requires preserving source-workspace operation where compatible).
2. **CLI package with a real `bin` mapping** — a `bin` entry exposing `gef`. *Not present today:* no package in the workspace declares `bin`. This is a design target for WO-002.
3. **Release artifacts with checksums** — optional; a self-contained binary remains *"a validated optimization, not a semantic architecture requirement"* (A9) and MUST NOT be promised before packaging tests prove equivalent cross-platform behaviour.

### 5.3 Packaging contract (designed)

| Aspect | Requirement |
|---|---|
| Package identity | one coordinated release; independently testable surfaces (`ARCHITECTURE.md` A2) |
| Contents | `dist/` output, `bin` shim, declared `engines`, bundled schemas (§6), `LICENSE`, `README` |
| `bin` mapping | single entry name `gef`, no additional aliases introduced without a governed decision |
| Entry execution | shim resolves the packaged entry without a shell pipeline; Windows/Linux/macOS parity required |
| Install verification | post-install self-check must be runnable and must fail closed |
| Uninstall/cleanup | removes only files it installed; never deletes user project data under a GEF-managed target |
| Cross-platform | Windows, Linux, macOS; path/case/symlink/line-ending assumptions explicit and tested (A9, cross-platform policy) |
| Lockfile | production builds pin dependency lockfiles and produce verifiable metadata (A9) |

### 5.4 Publication honesty gate

Until release evidence exists, the documentation MUST describe distribution as a **designed, unproven** model. The `README.md` statement that no npm package or global executable is available remains correct for V1.0.0 and MUST NOT be contradicted by speculative V1.1 prose.
