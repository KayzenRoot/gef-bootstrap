## 1. Selection model

Validation selection is a **closure computation over a known graph** plus an **uncertainty gate**. It is never a heuristic guess.

```text
changed semantic units
        │
        ▼
  [1] SOURCE→TEST MAP        (direct dependencies)
        │
        ▼
  [2] REGRESSION RADIUS      (dependent closure)
        │
        ▼
  [3] UNCERTAINTY GATE       ◄── the critical control
        │
   ┌────┴─────┐
   ▼          ▼
CERTAIN    UNCERTAIN
   │          │
   ▼          ▼
L0–L3       escalate (L4 and/or L5)
```

### 1.1 Ladder levels (reused, not redefined)

`L0` structural/static · `L1` direct tests · `L2` impacted closure · `L3` boundary tests · `L4` risk expansion · `L5` exact-head assurance.

### 1.2 Core rule — never silently omit

**A test may be excluded only when the selector can positively prove it is unaffected.** Absence of evidence of impact is not evidence of absence of impact.

Consequences:

- An unknown dependency edge widens the selection; it never narrows it (`D-0023`: *"Unknown dependencies widen context/validation"*).
- An unmapped changed file resolves the selection to `L4` or `L5`.
- Missing dependency-closure knowledge MUST NOT be converted into a smaller test radius (`EXECUTOR-ACCELERATION-CONTRACT.md` §16).
- The selector's output MUST carry its own confidence state; `INDETERMINATE` escalates.

### 1.3 Escalation triggers (mandatory)

Any of the following forces escalation:

| Trigger | Minimum escalation |
|---|---|
| changed file absent from the source→test map | `L4` |
| dependency endpoint unknown | `L4` |
| changed contract/schema crossing a persistence, process or provider boundary | `L3`, plus `L5` at close |
| security/integrity-relevant surface touched | `L4`, plus `L5` at close |
| assurance policy classifies the change `ELEVATED` | `L5` at close |
| selector confidence `INDETERMINATE` | `L4` |
| failure in the impacted closure | failure-scoped retest, then `L4` |
| brownfield project without adopted shadow assurance (`D-0014`) | full suite; selective selection not yet authoritative |

### 1.4 Assurance override

`D-0024` and `ADR-0002-D7` hold: budgets never override the assurance floor. Selective validation saves **repeated intermediate work**; it never removes the required exact-head sweep. `selectedTests.finalSweepRequired` in the Execution Capsule records the obligation explicitly.

## 2. Proof reuse model

A previously green result may suppress repeated work **only** through a `Test Proof Reuse Receipt` (TPRR) proving every relevant binding unchanged. The binding dimensions are canonical in `EXECUTOR-ACCELERATION-CONTRACT.md` §10 and are not restated as a competing list here.

### 2.1 Eligibility

A proof is `REUSABLE` only when **all** hold:

1. **Lineage** — the proof binds to an identifiable, immutable prior state (commit/tree or equivalent), not to a moving branch (`D-0036`).
2. **Source fingerprints** — the impacted source/contract semantic digests are unchanged.
3. **Dependency impact** — the dependency-closure digest is unchanged.
4. **Configuration** — the relevant configuration digest is unchanged.
5. **Toolchain/runtime** — the compatibility fingerprint is unchanged.
6. **Platform** — where behaviour may vary by platform, the platform identity matches.
7. **Fixtures** — test fixture/data identity matches where applicable.
8. **Policy** — the assurance policy identity is unchanged; a stricter policy invalidates reuse.
9. **Validity** — the TPRR state is exactly `REUSABLE`. All other states (`STALE_SOURCE`, `STALE_TEST`, `STALE_CONFIG`, `STALE_TOOLCHAIN`, `PLATFORM_MISMATCH`, `DEPENDENCY_UNKNOWN`, `CONFLICT`, `INDETERMINATE`) forbid suppression.

A cached `PASS` string is never proof (`ADR-0002-D6`).

### 2.2 Invalidation

Invalidation is targeted, not global, and follows the smallest safe granularity (`D-0023`). A change to a source, test, configuration, toolchain, platform assumption, fixture or policy invalidates **only the proofs whose dependency closure contains it**, plus any proof whose closure is unknown (which is treated as invalid rather than reused).

**Expiration.** Proof reuse MAY additionally carry an explicit expiry. Absent an expiry, invalidation is purely dependency/fingerprint-driven. Expiry is a conservative narrowing only — it can never extend eligibility beyond §2.1.

### 2.3 Credit boundary (hard rule)

> **No proof reuse may manufacture production credit.**

Operationally:

- Reuse suppresses a repeated *intermediate* invocation only.
- Reuse NEVER contributes to production acceptance accounting, the `1088` denominator, MODULE_DONE promotion, or any release gate.
- Final acceptance evidence MUST be produced by actual execution at the exact candidate head (`ADR-0002-D7`, `D-0034`, `D-0036`).
- A reused proof is not a Work Order completion claim and cannot satisfy a final-sweep obligation.
- The Execution Capsule schema encodes this as `proofReferences[].manufacturesProductionCredit: const false`.

### 2.4 Brownfield shadow-assurance precondition

In an adopted project, aggressive reuse MUST NOT become authoritative before shadow assurance proves the impact model on that project's actual dependency graph (`D-0014`, `ADR-0002-D6`). Until then, selection runs in shadow mode (selected set recorded and compared against the full suite) rather than in suppression mode.

## 3. Failure-scoped retest

Reused, canonical from `EXECUTOR-ACCELERATION-CONTRACT.md` §11: record failure fingerprint → fix only the relevant surface → rerun the failed test → rerun the impacted closure → broaden only after the local failure clears or when the failure indicates systemic risk.

A failure **invalidates** overlapping proofs conservatively: any proof whose closure contains the failed or changed surface becomes non-`REUSABLE`. Restarting a full suite after every small correction when unaffected proofs remain compatible is prohibited.

---

## 4. Interaction with the environment

Incremental validation reduces work; it never removes repository-level obligations. On this repository the repository-wide `Repository validation` check and the required exact-head sweeps remain mandatory and are not subject to selector suppression.

## 5. Acceptance obligations for WO-006 / WO-007

1. Selecting with an unmapped changed file yields escalation, not a smaller set (negative test).
2. `INDETERMINATE` selector confidence cannot produce suppression (negative test).
3. Every non-`REUSABLE` TPRR state forbids suppression (state-matrix test).
4. A reused proof never increments production credit — asserted by test, not prose.
5. Targeted invalidation: changing one file invalidates only proofs whose closure contains it.
6. Brownfield shadow mode precedes suppression mode in an adopted project.
7. L5 is never waived by successful L1/L2 when policy requires the sweep.
