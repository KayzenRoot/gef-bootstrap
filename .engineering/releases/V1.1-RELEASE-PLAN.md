# GEF Bootstrap V1.1 Release Plan

Status: `PLANNING_ACTIVE`
Baseline: `v1.0.0`
Target: `v1.1.0`
Risk: `STANDARD`, escalating to `ELEVATED` for upgrade/migration/recovery and release promotion.

## Increment sequence

### GBS-V11-WO-001 — Release foundation and compatibility lock
Define V1.1 contracts, CLI architecture, distribution strategy, compatibility policy, stable-main release channel, benchmark baseline and test plan. No broad implementation before this gate is audited.

### GBS-V11-WO-002 — CLI + distribution
Implement the supported command entrypoint and install/distribution path with deterministic exit codes, structured output where required, help/version contracts and cross-platform smoke coverage.

### GBS-V11-WO-003 — Doctor 2.0 + status
Implement environment/repository diagnostics and actionable remediation without destructive automatic repair.

### GBS-V11-WO-004 — Upgrade + compatibility + recovery
Implement preservation-first upgrade planning/apply, dry-run, compatibility matrix enforcement, transactional failure behavior and rollback/roll-forward evidence.

### GBS-V11-WO-005 — Context Compiler + Execution Capsule
Optimize task/context compilation using fingerprints, relevance, cache and delta context. Emit a deterministic Execution Capsule containing only required sources, files, constraints, tests and STOP CONDITION.

### GBS-V11-WO-006 — Test Impact + Incremental Validation
Select the minimum proven validation set. Uncertainty MUST escalate rather than silently omit required tests.

### GBS-V11-WO-007 — Proof Reuse + invalidation
Reuse evidence only when lineage, fingerprints, policies and relevant dependencies remain compatible. Invalid evidence must be rejected explicitly.

### GBS-V11-WO-008 — Performance telemetry + benchmark
Measure comparable executor cycles, wall-clock duration, context size, validation volume, cache/proof reuse and retries. Do not claim speedup from incomparable populations.

### GBS-V11-WO-009 — Integrated assurance + docs/runbooks
Cross-platform regression, security, migration/recovery, CLI E2E, documentation, install/upgrade runbooks and release-candidate hardening.

### GBS-V11-WO-010 — Production acceptance and promotion
Exact-head independent audit. Promote to `main` and tag `v1.1.0` only after objective acceptance. Until then `main` remains the current production-approved release.

## Performance goals
Goals are benchmark targets, not acceptance facts until measured:
- reduce executor context volume for representative governed work;
- reduce unnecessary validation work while preserving fail-closed assurance;
- reduce repeated repository rediscovery through deterministic cached/fingerprinted context;
- demonstrate no material regression in correctness, security, recovery or evidence integrity.

## Promotion rule
`release/1.1` MUST NOT replace `main` merely because implementation is complete. Required state is FUNCTIONAL + TESTED + DOCUMENTED + BENCHMARKED + AUDITED + PRODUCTION_ACCEPTED. Promotion is exact-head and evidence-bound.
