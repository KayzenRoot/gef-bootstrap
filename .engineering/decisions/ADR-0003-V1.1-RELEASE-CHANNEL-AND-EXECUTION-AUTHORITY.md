# ADR-0003 — V1.1 Release Channel, Execution Authority and CLI Admission

Status: `PROPOSED_FOR_WO_001_AUDIT`
Release line: `1.1.x`
Base: `release/1.1`
Supersedes (bounded): `ADR-0002-D8` for the V1.1 release line only
Related decisions: `D-0004`, `D-0047`, `D-0036`, `D-0042`

This ADR is produced by `GBS-V11-WO-001`. It is a governed decision record submitted for objective audit; it does not by itself promote V1.1 or modify `main`.

## Trigger

Three triggers require an explicit governed decision before broad V1.1 implementation:

1. **Release-channel gap.** V1.0.0 is production accepted and `main` is the production-only branch, but no governed document yet codifies what `main`, `release/1.1` and `1.0.x` mean relative to one another during next-release development.
2. **Execution-authority conflict.** Three approved frozen sources state the same invariant. `ADR-0001`: *"GEF Bootstrap continues to be built entirely through ChatGPT and connected project tools; Codex is not its implementation executor."* `ADR-0002-D8`: *"GEF Bootstrap itself continues to be implemented through ChatGPT and connected project tools only. Codex/external executors may be used in target repositories governed by GEF, not to build this repository."* `ARCHITECTURE.md` restates it ("GEF Bootstrap itself is implemented through ChatGPT + connected tools, not Codex"), and `EXECUTOR-ACCELERATION-CONTRACT.md` §16 lists *"let Codex build the `gef-bootstrap` repository itself"* as a mandatory safety prohibition. However `.engineering/releases/V1.1-RELEASE-PLAN.md` assigns `GBS-V11-WO-001` through `GBS-V11-WO-010` — the construction of this repository — to Codex execution. This is a direct contradiction with approved frozen policy and is reported here rather than silently changed.
3. **CLI admission gap.** `D-0004` froze GEF Bootstrap as *"not a standalone application or CLI product."* `V1.1-SCOPE.md` NECESSARY item 1 requires *"Production-grade GEF CLI surface: `gef init`, `gef adopt`, `gef doctor`, `gef status`, `gef upgrade`."* `D-0047` permits admission of *"a future thin CLI/script/tooling layer … when it provides measurable ROI"* but does not itself admit the V1.1 CLI surface. Admission must be explicit.

## Decisions

### ADR-0003-D1 — Release channel contract
`main` is the **latest `PRODUCTION_APPROVED`** state of the product and the only branch permitted to represent production. V1.1 development occurs on `release/1.1` and its subordinate `feat/1.1/*` branches.

- `main` MUST NOT receive V1.1 feature work directly.
- `release/1.1` is **integration only** until V1.1 satisfies its release Definition of Done and is promoted. Its content is not production-approved merely because it builds or passes CI.
- Promotion to `main` is **exact-head and evidence-bound** (`D-0036`): the promoted commit must be the exact candidate head that passed the required assurance, security, cross-platform and Production Acceptance gates with `CRITICAL=0` and `HIGH=0`.
- Release tags are **immutable**. `v1.0.0` MUST NOT be moved, replaced or deleted. A future `v1.1.0` tag MUST point to the exact promoted commit and MUST NOT be created before acceptance.
- No tag, release or package publication occurs during V1.1 development branches.

### ADR-0003-D2 — Hotfix lineage and forward-port
A production defect affecting the V1.0 contract is corrected on a `1.0.x` hotfix lineage branched from `main`, shipped independently, and **forward-ported** into `release/1.1` where still applicable.

- A V1.0 hotfix MUST NOT be used as a route to deliver V1.1 features.
- Every `1.0.x` hotfix requires its own evidence and MUST NOT rewrite V1 accepted history.
- Forward-port is mandatory when the corrected defect remains present in `release/1.1`; the forward-port records the originating hotfix identity.
- Version numbering: `1.0.x` = patch maintenance; `1.1.x` = backward-compatible feature evolution; breaking contract changes require a major version or separately authorized next-version scope.

### ADR-0003-D3 — Conditional authorization for Codex execution of this repository (bounded supersession of ADR-0002-D8)
For the **V1.1 release line only**, Codex (or an equivalent external executor) is proposed to be authorized to implement this repository under the following mandatory bounds:

1. The executor operates **only** on `release/1.1` and subordinate branches. `main` is never a valid execution target.
2. Every execution MUST be bound to an admitted Work Order with a declared scope, base/head binding and STOP CONDITION.
3. The executor MUST NOT merge, tag, publish, force-push or rewrite history.
4. The executor MUST NOT modify V1.0.0 acceptance history, `.engineering/CHECKPOINT.md`/`CHECKPOINT.json` production state, or the `v1.0.0` tag.
5. Objective audit remains **external** to the executing agent. Executor self-assessment is not acceptance; the executor MUST NOT claim `APPROVED`.
6. Deterministic evidence (commands, exit codes, test counts, digests) is required; prose claims are not completion (`D-0034`).
7. Prompt-derived acceleration mechanisms (Execution Capsule, ENM, proof reuse) remain subordinate to canonical sources and MUST NOT silently decide scope, architecture, risk acceptance or semantic verdicts.

This supersession is **narrow**: once effective, it authorizes execution of this repository on the V1.1 release line. It does NOT repeal `ADR-0002-D8` for V1.0 lineage, does NOT authorize Codex on `main`, and does NOT make external execution the permanent implementation model for GEF. The permanent model remains an owner decision recorded by a later ADR when V1.1 closes.

This decision is governed by `D-0042`: a frozen decision may be reopened only through a recorded superseding decision with impact analysis, objective audit and checkpoint promotion. This ADR supplies the proposed superseding decision and impact analysis. **ADR-0003-D3 is not effective for subsequent implementation Work Orders until objective audit is APPROVED and the decision is promoted through the governed checkpoint flow.** WO-001 itself is treated as the bounded transition/proposal increment and cannot bootstrap continuing authority from its own executor claim.

### ADR-0003-D4 — CLI admission under D-0047
The V1.1 CLI surface is proposed for admission as the **thin deterministic mechanical layer** contemplated by `D-0047`, not as a reversal of `D-0004`.

Explicit bounds:

- The CLI is a **transport and rendering surface** over the existing application/library API (`ARCHITECTURE.md` A3). Business logic MUST NOT live in CLI handlers.
- The CLI MUST NOT become semantic authority for architecture, scope admission, requirements, risk acceptance or review verdicts.
- Canonical truth remains governed repository sources (`ARCHITECTURE.md`, frozen invariants).
- ROI obligation: `D-0047` admits the layer *"when it provides measurable ROI for deterministic tasks."* The V1.1 CLI therefore carries an explicit benchmark obligation under `.engineering/releases/V1.1-PERFORMANCE-BENCHMARK-PROTOCOL.md`. Failure to demonstrate comparative value is a governed finding against the CLI scope, not a silent continuation.
- The CLI MUST delegate to existing V1 engines rather than duplicating domain logic. The verified delegation surface is recorded in `.engineering/releases/V1.1-CLI-DISTRIBUTION-ARCHITECTURE.md`.

`D-0004`'s statement that GEF "is not a standalone application or CLI product" remains authoritative until this proposed admission passes objective audit and checkpoint promotion. After promotion, the statement remains true in the bounded sense that the CLI is not the product: the product remains the governed instruction/governance system, with a thin operator surface.

### ADR-0003-D5 — Distribution truthfulness
V1.1 design MAY specify an installable distribution model, but **no publication, package registration, binary artifact or install command may be described as available** until separately proven by release evidence.

- Designed ≠ proven. Documents MUST keep the two distinct.
- Until proven, the supported path remains the source workspace documented in `README.md`.
- Any distribution claim introduced before its evidence is a reporting defect.

## Consequences

- `main` remains the production branch and is untouched by WO-001.
- V1.1 has a proposed bounded release channel and proposed bounded external-executor authority, pending audit/promotion where `D-0042` requires it.
- The CLI has a proposed lawful path into the product without silently repealing `D-0004`.
- Two canonical conflicts (C3, C4) remain open with named owners rather than being silently normalized.
- No denominator change, no module inventory change, no V1.0 history change.
