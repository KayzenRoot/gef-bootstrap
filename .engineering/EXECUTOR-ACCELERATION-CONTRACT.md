# GEF Executor Acceleration Contract

Status: `OWNER_DIRECTIVE_APPROVED`
Owner decision: `ADR-0002-PLANNING-TO-EXECUTION-ACCELERATION`
Primary owners: `GBS-M28`, `GBS-M63`
Integrates: `M10`, `M11`, `M13`, `M14`, `M15`, `M26`, `M43`, `M45`, `M57`

## Purpose
Make target-project construction faster by moving deterministic/resolved engineering work left into ChatGPT-led planning, materializing a safe implementation seed, and giving the heavy executor an exact local recipe instead of a broad request to rediscover the repository.

The contract optimizes **time-to-governed-progress**, not minimum prompt length, minimum test count or maximum code generated by planning.

## Operating model

```text
DISCOVERY / PRODUCT PLAN
        ↓
ARCHITECTURE + MODULE/SESSION PLAN
        ↓
PLANNED FILE TOPOLOGY
        ↓
IMPLEMENTATION SEED COMPILATION
        ↓
EXECUTOR NAVIGATION MAP + CLOSED DECISIONS
        ↓
MARATHON EXECUTION PACK
        ↓
HEAVY EXECUTOR IMPLEMENTATION
        ↓
PROGRESSIVE IMPACT VALIDATION
        ↓
EXACT-HEAD ASSURANCE
        ↓
REVIEW / CHECKPOINT / NEXT WAVE
```

## 1. Planning-to-implementation split

### ChatGPT / planning side: resolve the light-but-expensive cognition
Planning SHOULD resolve as much as safely possible before executor invocation:
- architecture and module boundaries;
- target directory/file topology;
- file ownership and dependency edges;
- interfaces, public contracts, schemas and data shapes;
- algorithms/control-flow choices already justified by planning;
- invariants, error semantics, concurrency/transaction posture;
- known integration points;
- expected unit/integration/E2E cases;
- read/write scope;
- forbidden mutations;
- risk/assurance requirements;
- open questions that genuinely remain open.

### Heavy executor side: implement the expensive code
The executor SHOULD spend its budget on:
- completing nontrivial algorithms;
- integrating real libraries/framework APIs;
- implementing detailed branch/error logic;
- resolving compiler/runtime details not safely derivable during planning;
- writing production-grade tests and fixtures from the predeclared proof obligations;
- correcting implementation findings;
- performance/security hardening where required.

### Forbidden planning shortcut
Planning MUST NOT invent unresolved decisions merely to produce more seed code. Unknown remains unknown and is escalated.

## 2. Implementation Seed Tree
The **Implementation Seed Tree (IST)** is the planned target-repository structure materialized before heavy execution when safe.

Each seed entry has one of three modes:
- `NEW_FILE_SEED` — safe new file may be created with compile-safe structure;
- `EXISTING_FILE_PATCH_INTENT` — existing source remains untouched; exact planned edit is described separately;
- `STRUCTURE_ONLY` — directory/file is reserved but code is not yet safe to seed.

### Seed file content
A seeded source/test file SHOULD contain, where applicable:
1. module/file purpose;
2. owner/domain boundary;
3. imports/exports already decided;
4. types/interfaces/schemas;
5. public signatures;
6. invariants and error contracts;
7. algorithm outline;
8. dependency notes expressed as code-safe comments where useful;
9. explicit implementation TODOs;
10. expected test names/cases;
11. forbidden changes;
12. source/decision references through compact IDs, not copied essays.

### Compilation-Safe Seed rule
A seed must either:
- compile/typecheck/lint under the planned toolchain; or
- be explicitly excluded from build by the architecture with a declared activation gate.

Broken placeholder code is not an acceleration mechanism.

## 3. File Intent Capsule
Every planned file may have a compact **File Intent Capsule (FIC)** containing:

```yaml
file: packages/example/src/service.ts
mode: NEW_FILE_SEED
owner: module-x
purpose: deterministic domain operation
reads:
  - contract-a
writes:
  - artifact-b
imports:
  - ./types.js
exports:
  - createService
invariants:
  - no ambient clock
  - injected digest only
algorithm:
  - validate input
  - derive canonical state
  - compute result
  - seal receipt
required_tests:
  - deterministic permutation
  - cancellation
  - tamper detection
forbidden:
  - network access
  - repository-wide discovery
open_questions: []
```

The exact serialization format is selected during M63 implementation. The semantic fields above are required concepts.

## 4. Brownfield Patch Intent Capsule
For an existing healthy file, planning uses **BPIC** rather than rewriting the file early.

BPIC binds:
- target file identity/validity fingerprint;
- symbols/regions expected to change;
- before-contract assumptions;
- intended after-contract;
- dependent files/tests;
- insertion/replacement algorithm;
- preservation constraints;
- rollback/recovery note;
- uncertainty that requires executor inspection.

If the current file no longer matches the bound fingerprint, the patch intent becomes `STALE` and must be recompiled. It must not apply optimistically.

## 5. Executor Navigation Map
The **Executor Navigation Map (ENM)** is the default repository-entry surface for Codex/executors.

It MUST distinguish:
- `MUST_READ` files;
- `READ_IF_TRIGGERED` files;
- `WRITE_ALLOWED` files;
- `WRITE_FORBIDDEN` files/domains;
- symbol/dependency map;
- relevant tests;
- canonical decision/source IDs;
- known negative searches/capability gaps;
- safe expansion triggers.

### Search suppression rule
Repository-wide search is not performed merely because the executor is capable of it.

Search/expansion is justified by one of:
- referenced symbol missing;
- source binding stale;
- compiler/runtime evidence contradicts the pack;
- dependency endpoint unknown;
- unexpected brownfield structure;
- security/assurance rule requires broader inspection;
- explicit ambiguity remains.

Search results become new bounded context, not permission for unlimited rediscovery.

## 6. Decision Closure Capsule
The **Decision Closure Capsule (DCC)** lists architectural/product questions already resolved by canonical decisions.

For each closed question:
- decision ID;
- selected option;
- authority/source reference;
- relevant scope;
- reopen trigger.

Executor rule: do not spend reasoning budget reopening a closed question unless the reopen trigger is objectively present.

## 7. Marathon Execution Pack
A **Marathon Execution Pack (MEP)** may be long and may combine multiple compatible increments.

### Required sections
1. objective and expected forward progress;
2. exact execution base and validity bindings;
3. decisions not to reopen;
4. ENM read/write sets;
5. seed-tree inventory;
6. per-file intent capsules;
7. algorithms/implementation notes already resolved;
8. ordered execution waves;
9. atomic checkpoints inside the long run;
10. progressive validation plan;
11. reusable test-proof receipts;
12. failure/retry policy;
13. expansion/escalation triggers;
14. evidence outputs;
15. STOP CONDITIONS.

### Prompt length policy
No arbitrary short-prompt ceiling exists. A larger pack is preferred when the added material:
- removes ambiguity;
- prevents broad searches;
- removes repeated reasoning;
- allows more compatible increments to finish;
- gives exact tests/acceptance;
- reduces retry loops.

Redundant prose is still removed by the existing Prompt Entropy Reducer.

## 8. Execution Wave Fusion
Multiple increments/modules may share one executor invocation when all are true:
- dependencies/order are known;
- no unresolved CRITICAL/HIGH blocker in a predecessor;
- ownership/mutation domains are compatible;
- Work Orders permit the combined surface;
- each increment remains independently auditable;
- validation can attribute evidence to each increment;
- a failure does not force unsafe continuation into dependent work.

Wave categories:
- `SERIAL_REQUIRED` — dependency/risk forces order;
- `PARALLEL_SAFE` — independent tasks may run concurrently;
- `FUSED_SERIAL` — one long prompt executes several ordered increments;
- `DEFERRED` — blocked by missing truth/assurance.

## 9. Progressive Validation Ladder
M28 owns test-impact truth. M63 consumes it to reduce wall-clock cost.

### L0 — structural/static
Run only relevant format/schema/type/build/static checks required after the change.

### L1 — direct tests
Run tests directly mapped to changed symbols/files/contracts.

### L2 — impacted closure
Run dependent unit/component tests selected by the test impact graph.

### L3 — boundary tests
Run affected integration/API/persistence/provider boundaries.

### L4 — risk expansion
Run broader regression/security/platform checks when impact knowledge is incomplete or risk policy escalates.

### L5 — exact-head assurance
Run the full required Work Order/assurance suite on the final candidate head. This may include full regression, CodeQL/security, E2E and multi-OS matrices.

Passing L1/L2 does not waive L5 when L5 is required.

## 10. Test Proof Reuse Receipt
A prior PASS can skip repeated intermediate execution only when a **TPRR** proves compatibility of all relevant bindings.

Minimum binding dimensions:
- test identity and test-content digest;
- impacted source/contract semantic digests;
- dependency-closure digest;
- relevant configuration digest;
- toolchain/runtime compatibility fingerprint;
- platform identity where behavior may vary;
- test fixture/data identity where applicable;
- prior result/evidence identity;
- assurance policy identity;
- validity state.

States:
- `REUSABLE`;
- `STALE_SOURCE`;
- `STALE_TEST`;
- `STALE_CONFIG`;
- `STALE_TOOLCHAIN`;
- `PLATFORM_MISMATCH`;
- `DEPENDENCY_UNKNOWN`;
- `CONFLICT`;
- `INDETERMINATE`.

Only `REUSABLE` can suppress that repeated intermediate invocation.

## 11. Failure-Scoped Retest Loop
When a test fails:
1. record failure fingerprint;
2. fix only the relevant implementation surface;
3. rerun the failed test first;
4. rerun the impacted closure;
5. run broader regression only after the local failure is cleared or if the failure indicates systemic risk.

Do not restart a six-hour full suite after every small correction when unaffected tests already have compatible proof.

## 12. Exact-head full sweep
A selective test strategy MUST converge on a final exact-head assurance sweep according to module/Work Order intensity.

Full-sweep evidence is bound to the final candidate head/tree/config/runtime. Any subsequent production-code change invalidates affected final evidence and triggers the appropriate validation ladder again.

## 13. Seed drift
The **Seed Drift Sentinel (SDS)** compares the current repository with seed/navigation assumptions.

Drift classes:
- `NONE`;
- `LOCAL_COMPATIBLE`;
- `SEED_RECOMPILE_REQUIRED`;
- `CONTEXT_EXPANSION_REQUIRED`;
- `CONFLICT`.

Executor must not follow stale seed instructions blindly.

## 14. Performance metrics
M63/M43/M45/M57 SHOULD measure at least:
- wall-clock per executor invocation;
- useful increments completed per invocation;
- input/output tokens when observable;
- files read;
- broad searches executed;
- context expansions;
- executor reasoning/escalation branches where observable;
- total test invocations;
- duplicate test invocations avoided;
- full-suite invocations per Work Order;
- test-proof reuse rate;
- correction loops;
- rework ratio;
- cache/seed invalidations;
- defects escaping selective validation;
- final assurance duration.

No universal percentage improvement is claimed before M45/M57 baselines exist.

## 15. Prompt Progress Density
`Prompt Progress Density` is a benchmark concept, not a license to inflate prompts.

Candidate measurements include:
- accepted atomic increments / executor invocation;
- accepted changed semantic units / input-token bucket;
- accepted progress / wall-clock;
- files implemented correctly before first correction;
- rereads/searches avoided versus baseline.

Quality/assurance regressions invalidate a claimed optimization even if time/tokens improve.

## 16. Mandatory safety boundaries
Acceleration MUST NOT:
- replace canonical source authority with generated seed text;
- overwrite healthy brownfield source during planning without mutation authority;
- reuse a stale PASS;
- skip an assurance-required final suite;
- fuse modules across unresolved dependency blockers;
- let a long prompt hide multiple unauditable changes;
- convert missing dependency knowledge into a smaller test radius;
- treat prompt length or elapsed executor time as progress;
- let Codex build the `gef-bootstrap` repository itself.

## 17. Default target-project behavior
Unless a target project explicitly selects a stricter compatible profile, GEF SHOULD default to:
- planning-led seed generation;
- exact navigation maps;
- closed-decision capsules;
- long-horizon execution packs when useful;
- impact-first validation during implementation;
- proof-preserving reuse of unchanged green tests;
- exact-head assurance before acceptance.
