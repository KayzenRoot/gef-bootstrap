# GEF Bootstrap V1.1 Operations Runbook

Status: V1.1 development and release-candidate work. V1.1 is not a production release; WO-010 owns production acceptance, promotion to main and the v1.1.0 tag.

This runbook is written for project operators and for a new Codex/chat session continuing a governed application build. The repository checkpoint and admitted Work Order define the task. A conversation summary can help find context, but cannot promote state or authorize a new step.

## Supported source workspace

GEF Bootstrap is distributed as a source workspace. The CLI package is private to the workspace; do not use `npm install -g gef-bootstrap` and do not claim an npm package or standalone V1.1 executable.

Use Node.js 22, Git and npm on Windows, Linux or macOS.

For the current stable version, validate the immutable V1.0.0 source:

```bash
git clone https://github.com/KayzenRoot/gef-bootstrap.git
cd gef-bootstrap
git fetch origin --tags
git checkout --detach v1.0.0
git rev-parse v1.0.0
git rev-parse "v1.0.0^{commit}"
git status --short
npm ci
npm run validate
npm audit --audit-level=high
```

The V1.1 line is for admitted development and release-candidate validation. To inspect its source, check out `release/1.1` and validate before using it:

```bash
git fetch origin
git switch --track origin/release/1.1
npm ci
npm run validate
npm audit --audit-level=high
node packages/cli/bin/gef.mjs --help
```

Use the CLI help for the exact flags available in the checked-out commit. `init`, `adopt` and `upgrade` default to read-only plan/preview behavior. Apply requires the explicit `--apply` flag and an admitted, reviewed plan.

## Verify source identity, backup and permissions

For stable V1.0.0, record the source ref and compare it with the release identity before installing dependencies:

    git fetch origin --tags
    git checkout --detach v1.0.0
    git rev-parse v1.0.0
    git rev-parse "v1.0.0^{commit}"
    git status --short

The expected V1.0.0 tag object is aac89f9c3f0c884474958025bf14828bc338b5ee and its target commit is 866fe3af8cccc65c929aaf6a47a924401fa448b3. Stop if either value differs. If using a downloaded source archive, record its source URL and compute its SHA-256 on the downloaded file; compare against a publisher checksum when one is provided. A locally computed checksum detects later changes but does not authenticate the publisher. Do not describe an unsigned source as signed or provenance-verified.

Before applying an upgrade to an existing project, confirm the repository identity and branch, inspect git status, and keep a separate restorable backup of the target data or a verified version-control snapshot. Confirm the backup is readable before continuing. Preserve user-owned and untracked files; unknown or conflicting state is a stop condition. GEF's transaction journal supports recovery of the managed operation, but it is not a replacement for the project's backup.

Run with the least filesystem permission needed for the target. Use elevated local privileges only when a documented platform operation requires them; never broaden filesystem or provider access to make an unknown state pass.

## Before changing a project

1. Confirm the target repository and current branch, then read its `AGENTS.md`.
2. Read canonical project identity, source hierarchy, requirements, scope, architecture, Definition of Done, security constraints and current checkpoint.
3. Confirm the active Work Order is admitted and its Context Lock still matches the current source and exact base commit.
4. Inspect working-tree state and relevant provider state. Record exact repository, branch, commit/checkpoint identity and toolchain.
5. Preview effects. For brownfield work, inventory existing files and user changes; preserve unrelated data and stop on unknown/conflicting state.
6. Execute only the admitted scope. Capture tests, evidence and security results against the exact candidate head.
7. Run the owner audit against that same candidate. Then promote the checkpoint and name the next admitted Work Order/action.

Do not infer authorization from a past chat, successful historical run, open pull request or green checks from another commit.

## Upgrade, backup and recovery

Before a governed upgrade:

- Confirm the source is one of the migration-contract supported versions and the environment passes `gef doctor`.
- Inspect `gef status`, repository cleanliness and the exact source/receipt fingerprints.
- Preserve version control state and user-owned files. Keep GEF private recovery material, journals and receipts.
- Run the read-only `gef upgrade` preview. Confirm the source, destination version, plan digest, file effects and recovery requirements.
- Apply only the reviewed plan with `gef upgrade --apply`. Do not run apply from an unknown, dirty or conflicting state.

GEF retains the original source state and receipt byte-for-byte and writes a separate upgrade-state record through its transaction kernel. A verified repeat may report `NOOP_APPLIED`. It does not update the installed CLI or contact npm.

If an operation reports `RECOVERY_REQUIRED`, stop further apply attempts. Preserve the exact target tree and all `.gef-private` recovery journals, staging and evidence. Use read-only `gef doctor` and `gef status`, save their complete output and the candidate commit/checkpoint, and treat the project as blocked until the recovery material and observed state are reconciled. Never delete a journal or hand-edit managed files to force a pass. When the engine proves `RECOVERED`, re-run preview and review its new plan before any apply. If the result is unknown or conflicting, stop and escalate through a new bounded Work Order.

## Start every new project chat from canonical state

Before choosing or performing a construction step, the assistant must rehydrate from the live repository/provider state. Do not use prior chat history as the authority for progress, approvals, branch state, checks or next action.

1. Identify the exact project/repository and provider account. Verify the current branch and HEAD from the connected provider.
2. Read `AGENTS.md`, the current checkpoint in both canonical formats, source hierarchy, active Work Order, Context Lock, scope/requirements and the latest applicable evidence.
3. Verify checkpoint, branch/head, Work Order admission, source fingerprints, blockers and required check runs are current. Treat missing or stale inputs as unknown.
4. Apply the M18 resume rules: prove project/lineage/checkpoint continuity, observe drift, ignore conversation claims as authority, and stop for conflicts, stale bindings, orphan work or unresolved blockers.
5. Apply the M20 response rules: identify project and phase, active module/Work Order/stage, exact checkpoint/head, blockers and prerequisites; emit exactly one verified next necessary action when known.
6. If there is no safe legal action, say `NONE` or `UNKNOWN`, name the blockers and the evidence needed to clear them. Do not guess a successor or restart at an earlier stage merely because the chat is new.

During an admitted application build, route work through:

`DISCOVERY → REQUIREMENTS/SCOPE → ADMITTED WORK ORDER + CONTEXT LOCK → PREFLIGHT → IMPLEMENTATION → TESTS/EVIDENCE → EXACT-HEAD OWNER AUDIT → CHECKPOINT PROMOTION → NEXT ADMITTED WORK ORDER`

Every handoff must report the verified project and phase, active Work Order/stage, checkpoint/head, blocker and one next action. At a stop state, report `NONE/UNKNOWN` and the blocking prerequisite. The next chat follows that handoff by rechecking canonical state; it does not select work from conversation history.

## Release and optimization language

Until WO-010 completes production acceptance, V1.1 is development/RC only. V1.0.0 remains the stable production release.

WO-008 measured CLI ROI as `NO_CHANGE`; token counts were `UNAVAILABLE`, and `optimizationClaimEligible=false`. Keep those exact dispositions in later reports. Optimization goals remain targets until a comparable benchmark proves them.

## Stop conditions

Stop and report `BLOCKED` or `INDETERMINATE` when the checkpoint and provider state disagree, required evidence is missing/stale, a required check is not green on the exact head, a security or recovery blocker remains, or no canonical next action is available. Reconcile authority through a new governed decision or Work Order before continuing.
