## 1. Trigger, detection and adoption
The Domain Router examines explicit owner project brief FIRST, then validated manifests and dependencies, approved Scope/Architecture, chain configs and existing files: foundry.toml, Solidity/Vyper sources, hardhat.config.*, wagmi/viem, Anchor.toml, Cargo.toml Solana dependencies, on-chain program IDs, web3 references in approved requirements. Recognize `EVM_WEB3`, `SOLANA_WEB3`, `OTHER_WEB3_UNSUPPORTED_OR_RESEARCH`, `WEB3_FRONTEND_ONLY` and `BLOCKCHAIN_UNNECESSARY_OR_UNRESOLVED`. Never infer business authorization from a found Solidity test or wallet library. Existing project's approved blockchain/runtime always wins; no silent network, library or contract migrations. Ask only blocking questions. If a new unsupported chain is chosen, record extension contract and toolchain research rather than pretending EVM tests apply.

Interview additions (5–7 at a time, adapt to user replies):
- Which product action requires blockchain and why cannot conventional backend solve it? Chain/network, L1/L2, mainnet/testnet, EVM/Solana/other, desired portability and RPC/data requirements?
- Which assets or rules live on chain: payments, token, NFT, escrow, governance, exchange, royalty, game settlement, marketplace? Exact ownership rights, offchain alternatives and rollback impossibility?
- Who controls the contract, upgrades, pausing and emergency operations; multisig/timelock requirements; noncustodial versus custodial account boundaries and key custody?
- How should users connect/sign, what must be signed, wallet/chain switching, gas and failed/cancelled transaction UX, account recovery and privacy?
- Which tokens/standards, bridge/oracle/indexer, event finality/reorg tolerance, contract upgradeability, cross-chain assumptions, chain cost and latency budget?
- What is the maximum value/risk, threat model, applicable jurisdiction/regulatory questions requiring specialist input, external auditor need, disclosure and incident handling? No legal conclusion from project autodetection.
- Which environments and networks may Codex simulate, fork, test and deploy? NEVER assume authority for mainnet, irreversible contracts, high-value assets or paid RPC without owner-gated deployment policy.

Outputs: owner-approved chain decision ADR, trust/custody and attack boundary, onchain/offchain architecture diagram, key and transaction signing model, invariants linked to requirements, smart-contract upgrade plan or explicit immutable-deploy decision, infrastructure/cost/confirmation model, versioned exact chain config, risk-specific DoD and Codex Marathon WOs.

## 2. EVM verified starter technology stack
**Contract compiler and local test:** Solidity pinned solc and Foundry `forge/anvil/cast`; optionally Hardhat if existing ecosystem/TypeScript task requires it. Avoid installing Foundry AND Hardhat merely to appear complete. Local ephemeral Anvil and pinned block fork simulations; never use live key or network for PR CI.
**Security/library:** OpenZeppelin Contracts (roles, ownable/AccessManager, reentrancy protection, pausing, known implementations); if an upgradeable proxy is approved, OpenZeppelin Contracts Upgradeable plus Foundry Upgrades or core CLI with the previous implementation's storage layout as explicit reference. Never use unsafeSkipStorageCheck as routine. Upgrades are NOT automatically safe or necessary.
**Static and adversarial:** Slither for Solidity/Vyper static analysis; Foundry unit/fuzz/invariant for behavior; Echidna targeted deeper property/stateful campaigns; optional Medusa/Halmos/symbolic proving if supported, objectively useful and human-audited. Never label a fuzz pass formal mathematical proof or a replacement for independent security audit.
**App/client:** viem for typed RPC/ABI interaction and wagmi for React wallet handling when that frontend stack is approved; evaluate Reown AppKit/wallet connectors and EIP-6963 compatible discovery where multiple injected wallets are required. No wallet provider hard dependency for read-only dapps or other frontend stacks. Pin chain IDs, ABI hashes and contract addresses per deploy environment, never copy mainnet addresses into testnet.
**Indexing/events:** plain event listeners for simple low-scale apps; evaluate The Graph or self-hosted event indexer only when query/reorg/replay scale justifies it. Rebuild idempotently from block ranges, handle removed logs/reorgs, RPC failures and checkpoint block finality.
**Standards:** admit ERC-20/721/1155/4626, EIP-712 typed-signing, ERC-4337 account abstraction or other standards ONLY where product scope asks; preserve their threat-specific tests and chain capability checks, no generic all-ERC installation.

## 3. First-party GEF Web3 mechanisms (candidate proposals, not new mandatory M identifiers)
W3-01 Smart Contract Guardian: extend existing Bug Hunter, Contract Change Sentinel, Security Engine and Proof Graph. Link each approved invariant to examples, Foundry fuzz, cross-function stateful sequence, Slither issue triage, deeper Echidna property campaigns where high-risk. Risk floors: no ignored HIGH/CRITICAL, security questions cannot be waived by FAST interview.
W3-02 Economic Invariant Compiler: bind user-approved supply, reserve, vault/escrow conservation, no negative balances, ownership and transfer caps, fee bounds, withdrawal/settlement, rounding and precision to executable deterministic property harness and adversarial actors. Distinguish economic assumptions from mechanically enforceable invariants and oracle external assumptions. Use independent modeling on high-value logic.
W3-03 Contract Upgrade Sentinel: for upgradeable contracts compare original/new storage layout and ABI/event behavior, initializer/reinitializer authorization, proxy admin rights, governance/timelock delay, migration behavior and safe halted fallback. Unknown layout/no reference BLOCKS; fixed immutable deployments instead verify no unauthorized privileged upgrade surfaces.
W3-04 Transaction and Signature Sentinel: chain ID, account type, domain separator, expiration, nonce/replay, spender allowance, permit/typed data, wrong chain, malicious signature request, fee simulation, transaction replacement, pending/failure/cancelled, partial indexing and user-readable transaction preview.
W3-05 Deployment and Key Guardian: deploy manifests, verified bytecode/build provenance, code hash, exact chain/network/RPC and safe signer policy. Testnet dry run; multisig/timelock/external approval and independent audit when defined by asset/risk class; no seed phrase or private key in ChatGPT, GitHub comments, CI logs, local fixture repos or raw telemetry. Mainnet deploy is separately explicitly authorized and can never result from implicit “continue.”
W3-06 Chain Reality Lab: Anvil fork at PINNED block and chain identity, multi-RPC disagreement/reorg/confirmation simulation, event dedup/reconciliation, oracle stale/manipulation and cross-chain bridge failure tests. Avoid mutable latest-fork inputs in golden tests.
W3-07 Smart Contract Cost Engine: measured gas and deployment bytes against approved budgets on pinned compiler and fixture, not fabricated “cheap gas”; optimization cannot trade security or legibility for gas. L1/L2 fees and sequencer trust/exit risks are independent assumptions.
W3-08 Onchain/Offchain Consistency Guardian: explicit ledger of chain state vs indexer/backend materialized views with block heights, confirmations, reorg reversal and idempotent compensation. Sensitive financial operations use a reversible offchain pending state until chain finality and approved business semantics permit transition.

## 4. Validation ladder and hard gates
P0 pin chain/solc dependencies, source tree, ABI, reference storage version and security classification. NO mainnet secrets or write credentials.
P1 compile/format + static security (Slither where EVM).
P2 deterministic Foundry unit, errors, role/access, signature and simple invariant tests; seeded fuzz repeatability.
P3 multi-contract integration and fork-at-pinned-block; indexer/reorg/failed transaction, endpoint outage and per-network contract address tests.
P4 stateful/Echidna campaigns on risk-critical contracts; differential/model and symbolic only when cost/evidence warrants. Record campaign seeds, call sequences, coverage limit and duration; high-risk independent review still applies.
P5 if upgradeable: prior-layout/OpenZeppelin validate + initializer/role/governance/rollback/incident rehearsal. If immutable: prevent pretending code can be rolled back.
P6 high-value or finance/RMT: threat model, independently qualified expert audit or explicitly documented owner risk decision per approved gate, key ceremony, freeze/upgradeability policy and emergency plan.
P7 only approved testnet/prod deployment operations, exact-head artifact, verified source and address, smoke, role verification, monitoring/incident and owner-accepted release gate. No code-generation run implicitly spends assets.

Acceptance negative fixtures: unprotected withdraw, reentrancy and invariant violation, rounding profit, duplicate message/nonce replay, malicious chain mismatch, stale oracle, bridge message replay, wrong proxy layout, unchecked initializer, rogue role escalation, wrong chain/address, dev key leak, unconfirmed transfer counted as settled. Keep deterministic fixtures from each valid found defect.

## 5. Solana is a SEPARATE chain-specific adapter
Rust + Anchor if approved; `anchor test`/local validator appropriate; LiteSVM for deterministic fast integration in Rust/TS/JS/Python and Mollusk for isolated Rust instruction harness; optional coverage-guided Crucible fuzzing if this project's architecture and tool maturity warrant. Verified Anchor testing catalog: https://www.anchor-lang.com/docs/testing and https://solana.com/docs/programs/testing/mollusk .
Solana-specific risks: signer and writable account constraints, PDA seed/collision assumptions, owner validation, arbitrary CPI/program ID injection, token program/interface type, account size/rent and compute units, transaction atomicity and upgrade authority. Do NOT apply Solidity Slither/Echidna/Foundry to Rust programs and claim coverage.
A fully distinct upgrade/control/fee/finality and wallet adapter is required. Other chain frameworks must be separately admitted after current documentation/security proof.
